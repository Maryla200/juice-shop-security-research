📅 تاریخ: ۲۵ مرداد ۱۴۰۵ ✅ چالش حل‌شده: Login Admin

🧪 گزارش تزریق SQL و ورود به پنل ادمین

OWASP Juice Shop — حمله‌ی تزریق SQL برای دورزدن احراز هویت

🎯 ۱. شرح چالش

هدف: ورود به حساب کاربری مدیر (administrator) بدون داشتن رمز عبور، با استفاده از آسیب‌پذیری تزریق SQL در فرم لاگین.

چالش Login Admin یکی از چالش‌های ابتدایی اما بسیار مهم در OWASP Juice Shop است که نحوه‌ی سوءاستفاده از ورودی‌های کاربر را نشان می‌دهد.

🛠️ ۲. گام‌های اجرایی

۱

شناسایی فرم لاگین

فرم لاگین در آدرس http://127.0.0.1:3000/#/login قرار داشت.

درخواست لاگین به آدرس زیر ارسال می‌شد:

POST /rest/user/login HTTP/1.1

بدنه‌ی درخواست به صورت JSON بود:

{
  "email": "[ایمیل]",
  "password": "[رمزعبور]"
}
۲

تزریق کد مخرب در فیلد ایمیل

در فیلد ایمیل، کد زیر وارد شد:

' OR 1=1;--

و در فیلد رمزعبور هر مقدار دلخواه (مثلاً abc) وارد شد.

📖 نحوه‌ی عملکرد:

این کد باعث می‌شود کوئری SQL به‌جای بررسی ایمیل و رمز، همیشه TRUE برگرداند و اولین کاربر موجود در دیتابیس (که در جوی‌شاپ ادمین است) را لاگین کند.

۳

بررسی کوئری ساخته‌شده

کوئری SQL که در پشت‌صحنه اجرا می‌شود، به شکل زیر خواهد بود:

-- کوئری اصلی در سرور
SELECT * FROM users
WHERE email = '' OR 1=1;--'
AND password = 'abc'

بخش ' OR 1=1;-- باعث می‌شود شرط WHERE همیشه درست باشد و بخش -- نیز بقیه‌ی کوئری را به‌عنوان توضیح (comment) غیرفعال می‌کند.

۴

نتیجه‌ی نهایی

✅ چالش با موفقیت حل شد!

پس از ارسال درخواست، سرور پاسخ 200 OK همراه با توکن احراز هویت ادمین برگرداند و پیام زیر نمایش داده شد:

// پاسخ سرور
{
  "authentication": {
    "token": "eyJhbGciOiJSUzI1NiIs...",
    "bid": 1
  }
}

توکن دریافت‌شده نشان‌دهنده‌ی ورود موفق با نقش ادمین است.

🔍 ۳. جزئیات فنی درخواست و پاسخ

⚠️ ۴. تحلیل آسیب‌پذیری

  • علت آسیب‌پذیری: ورودی کاربر (ایمیل) بدون هیچ‌گونه پالایش یا پارامتری‌سازی، مستقیماً در کوئری SQL قرار گرفته است.
  • نوع حمله: SQL Injection از نوع تزریق مبتنی بر خطا که با تغییر منطق کوئری، احراز هویت را دور می‌زند.
  • شدت آسیب‌پذیری: بالا (Critical) — زیرا مهاجم می‌تواند بدون نیاز به رمز، به‌عنوان مدیر وارد سیستم شود.
🛡️ راهکار پیشنهادی برای رفع:
  • استفاده از Parameterized Queries (کوئری‌های پارامتری) یا ORM.
  • اعتبارسنجی و پالایش ورودی‌های کاربر (Input Validation).
  • استفاده از حداقل امتیاز (Least Privilege) برای اتصال به دیتابیس.

📝 ۵. جمع‌بندی

در این حمله، با استفاده از یک تزریق SQL ساده در فیلد ایمیل فرم لاگین، موفق شدیم به‌عنوان مدیر (admin) وارد سیستم شویم و چالش Login Admin را با موفقیت حل کنیم.

این آزمایش نشان می‌دهد که چگونه عدم پالایش ورودی‌های کاربر می‌تواند امنیت کل سیستم را به خطر بیندازد و اهمیت استفاده از روش‌های امن کدنویسی را آشکار می‌کند.

✅ درس آموخته: هرگز به ورودی‌های کاربر اعتماد نکنید. همیشه آن‌ها را قبل از استفاده در کوئری‌های پایگاه داده، پالایش یا پارامتری کنید.
